# Story 3.1: Personen-Selektor & Mehrpersonen-Ansicht Tag/Woche mit Privat-Default

Status: done

## Story

As a Teammitglied,
I want eine Teilmenge meiner Kollegen auswählen und deren Verfügbarkeit nebeneinander sehen, ohne ihre echten Termindetails einzusehen,
so that ich in Sekunden erkenne, ob jemand ansprechbar ist, ohne nachzufragen oder ihre Privatsphäre zu verletzen.

## Acceptance Criteria

1. **Given** ich bin in der Tages- oder Wochenansicht, **when** ich auf den "+"-Chip des Personen-Selektors klicke (oder ihn per `Enter`/`Space` aktiviere), **then** öffnet sich ein durchsuchbares Dropdown mit der Team-Roster-Liste; Tippen filtert in Echtzeit, Pfeiltasten navigieren durch die gefilterten Treffer, `Enter` fügt die fokussierte Person als neuen Avatar-Chip hinzu und hält das Dropdown offen, `Esc` schließt es ohne Auswahl und gibt den Fokus an den "+"-Chip zurück.
2. **Given** ich habe mehrere Kollegen ausgewählt, **when** die Mehrpersonen-Ansicht rendert, **then** erscheinen ihre Kalender nebeneinander in Spalten (nie überlagert), meine eigene Spalte zuerst/angeheftet, mit unbegrenzter Anzahl an Spalten — die Reihe scrollt horizontal statt eine Obergrenze zu erzwingen.
3. **Given** eine fremde Spalte (ich bin weder Eigentümer noch Teilnehmer eines dort gezeigten Termins), **when** die Spalte rendert, **then** zeigt jeder Zeitblock ausschließlich einen Status-Block ("privat/beschäftigt" + Verfügbarkeits-Status) — nie Titel, Teilnehmer oder Ort, unabhängig davon ob der Termin nativ oder synchronisiert ist.
4. **Given** ich bin selbst als Teilnehmer in einem fremden nativen oder synchronisierten Termin eingetragen, **when** ich diesen Termin in der Kollegen-Spalte anklicke, **then** öffnet sich das Detail-Popover im Vollmodus (Titel, Zeit, Teilnehmer) — die Teilnehmer-Ausnahme aus FR-9 gilt unabhängig von der Terminquelle.
5. **Given** ich bin weder Eigentümer noch Teilnehmer eines fremden Termins, **when** ich ihn anklicke, **then** öffnet sich das Detail-Popover im Status-only-Modus mit explizitem Datenschutzhinweis ("Details sind privat — nur der Status ist sichtbar."), niemals eine leere oder wie defekt wirkende Karte.
6. **Given** die Filterung nach Eigentümerschaft/Teilnahme, **when** ein beliebiger API-Endpoint Termindaten für einen Betrachter ausliefert, der weder Eigentümer noch Teilnehmer ist, **then** liefert die API die vollen Felder (Titel, Teilnehmer, Ort) zu keinem Zeitpunkt aus — die Filterung läuft serverseitig durch `AppointmentViewService`, eine rein clientseitige Ausblendung erfüllt die Anforderung nicht.
7. **Given** die Mehrpersonen-Ansicht für mehrere ausgewählte Personen gleichzeitig, **when** Termine für alle Spalten geladen werden, **then** verwendet das System eine Bulk-Methode auf `AppointmentViewService` — kein zweiter Codepfad reimplementiert die Privat-Default-Regel eigenständig für "mehrere Personen gleichzeitig".
8. **Given** ich wähle keine Kollegen aus, **when** ich die Mehrpersonen-Ansicht öffne, **then** rendert meine eigene Spalte weiterhin vollständig, der verbleibende Raum zeigt den "+"-Chip mit einladendem Text ("Wähle Teammitglieder, um ihre Verfügbarkeit zu sehen."), keine leere Fläche.
9. **Given** ich wechsle zwischen Tages- und Wochenansicht, **when** ich vorher Kollegen ausgewählt hatte, **then** bleibt die Auswahl erhalten.
10. **Given** ich klicke auf das "×" an einem Avatar-Chip, **when** die Aktion ausgeführt wird, **then** wird die Person sofort ohne Bestätigungsdialog aus der Auswahl entfernt.
11. **Given** ich nutze ein mobiles Endgerät mit vielen ausgewählten Spalten, **when** ich die Mehrpersonen-Ansicht öffne, **then** funktioniert horizontales Scrollen identisch zur Desktop-Ansicht, keine Obergrenze für die Auswahl.
12. **Given** ein Zeitblock in einer Kollegen-Spalte, **when** er einer Assistive-Technologie vorgelesen wird, **then** trägt er ein Label wie "Termin, Status: Bitte nicht stören" (Status only, nie Titel) — UX-DR33.

## Dev Notes

### Architecture compliance

- **AD-3** is this story's central rule and this story's Task 1 is where it gets structurally enforced: *one* Application-layer method (`GetForViewerByIdAsync`) now decides full-vs-status-only for **every** single-appointment read, own or foreign — there is no second "is this a colleague's appointment" branch anywhere else in the codebase after this story. The bulk method (`GetForViewersAsync`) is intentionally simpler than AD-3's example signature `GetForViewers(personIds, range, viewerId)` — **`[ASSUMPTION]`**: this story's own AC 3 requires colleague-column blocks to be status-only unconditionally (no attendee exception at the inline-block level — the FR-9 attendee exception only ever surfaces through the *detail popover*, per AC 4/5 and EXPERIENCE.md's Component Patterns table: *"Every other column renders status-blocks only (click → status-only popover, or full detail if the viewer is a listed attendee)"*). Since the bulk wire shape (`ColleagueAppointmentSlotResponse`) never carries a `Title` field at all, a `viewerId` parameter on `GetForViewersAsync` would compute data the endpoint could never expose — dead logic. If a future story needs bulk full-detail-aware slots, add the parameter then; don't build it speculatively now.
- **AD-13** (RFC-7807, stable codes): both endpoints already reuse `ProblemResults.Problem(...)` for their one error case (`invalid-request` for `from > to`); no new error codes needed.
- **UX-DR7/UX-DR12/UX-DR13/UX-DR18/UX-DR25/UX-DR27/UX-DR39** are this story's UX-Spine scope (see epics.md Story 3.1 "Enthält zusätzlich").

### Existing code this story touches (read before changing)

- `src/Application/Appointments/IAppointmentViewService.cs` / `src/Infrastructure/Appointments/AppointmentViewService.cs` — `GetOwnAppointmentByIdAsync` is **removed**, not deprecated-alongside — the endpoint that called it is rewritten in the same PR (Task 2), so there's no dangling caller. `GetOwnAppointmentsAsync` is untouched.
- `src/Api/Endpoints/AppointmentEndpoints.cs` — `GET /api/appointments/{id:guid}`'s behavior changes for non-owned appointments (404 → 200 status-only). `POST /api/appointments` and `GET /api/appointments` (own bulk) are untouched.
- `src/Api/Contracts/AppointmentContracts.cs` — `AppointmentDetailResponse` gains `IsFullDetail` and its `Title`/`StartUtc`/`EndUtc`/`Attendees` become nullable. Anything else constructing this record (only `AppointmentEndpoints.cs` does) must be updated for the new constructor shape.
- `frontend/src/app/pages/home/calendar/calendar.service.ts` — `AppointmentDetail` interface reshaped; `getAppointmentDetail`'s call site (`appointment-detail.ts`) is the only consumer, updated in the same PR (Task 7).
- `frontend/src/app/pages/home/calendar/overlap-layout.ts` and `date-utils.ts`'s `groupByDay` — widened to generics; verify no other caller assumes the concrete `Appointment` type in a way the generic breaks (check `month-view.ts`'s use of `groupByDay` — Story 3.2's territory, but this story's Task 4 change must not break it).
- `frontend/src/app/pages/home/calendar/calendar-column/calendar-column.ts`/`.html` — gains `mode` input; `home.html`'s existing own-column usages (`week`/`day` cases) don't need to change since `mode` defaults to `'own'`.
