# Adversarial Review: PRD "Team-Terminkalender mit Synchronisation"

**Reviewer stance:** Cynical, zero patience for hand-waving. Assume every unstated case has a way of biting someone. This review focuses on what the PRD *adds* to the already-reviewed brief — FR-level detail, NFRs, constraints — and asks whether that detail actually survives contact with implementation, daily use, and a security audit.

## Overall Verdict

The PRD is a genuine improvement over the brief: FRs are numbered, most have testable consequences, and it's unusually honest about its own assumptions (`[ASSUMPTION]` tags, an Assumptions-Index, an Offene-Fragen section). That candor is real credit. But the document has one severe, load-bearing gap — it never states *where* the privacy redaction (FR-9) is enforced, which means the entire "Grundlage des Vertrauens" claim in section 4.4 could be defeated by anyone who opens browser dev tools. There's also a concrete internal contradiction between FR-3 and FR-4 on the `Ort` field, a real gray zone in the FR-10 heuristic that swallows the most common meeting lengths, and a cluster of missing operational/security FRs (team member onboarding/offboarding, token storage, auth model) that a self-hosted tool holding a whole team's real calendar contents cannot skip, even as a prototype. None of these are fatal to proceeding, but none should be waved off as "architecture will figure it out" either — several are product decisions, not implementation details, and belong in this document.

**Recommendation:** Fix the FR-3/FR-4 `Ort` contradiction and add one explicit sentence establishing server-side enforcement of the Privat-Default before this PRD is used to greenlight architecture work. Everything else can be logged as open questions, but should be logged — right now several aren't mentioned anywhere, including Non-Goals.

## Critical

1. **The Privat-Default's enforcement point is never specified — this is the whole product's trust claim, left as an implementation detail.** Section 4.4 states the separation between what the tool reads and what it shows "ist die Grundlage des Vertrauens in das Tool," and FR-9 says "Kein UI-Pfad ... zeigt einem Teammitglied den echten Titel." But "UI-Pfad" is exactly the wrong unit of enforcement to promise: if the backend API returns full event data (title, attendees) for every visible event and the frontend merely chooses not to render it, any team member can open browser dev tools / inspect network responses and read every colleague's real meeting titles and attendees in plaintext. Nothing in FR-8, FR-9, or the Constraints section says filtering must happen server-side, per viewer, per request. Given the brief's addendum already established that "Privat-Default ist eine Anzeigeregel, keine Datenzugriffsgrenze" (repeated verbatim in PRD §8), the PRD needed to add the one sentence the brief couldn't: *where* that display rule is enforced. As written, a competent junior developer could ship exactly the architecture that breaks the product's central promise on day one, and nothing in this PRD would flag it as wrong.

2. **FR-3 and FR-4 contradict each other on the `Ort` field.** FR-4 (Termin-Detailansicht, Must-Have) promises the detail view shows "Ort falls vorhanden" for a user's own appointments. FR-3 (Termin anlegen, Must-Have) lists the creatable fields as "Titel, Datum/Uhrzeit, Dauer und optionalen Teilnehmern" — no `Ort`. The only FR that introduces a location field is FR-15 (Should-Have, explicitly out of MVP scope, bundled with autocomplete + map). So for a native event created via the MVP's own FR-3, there is no way to ever populate the `Ort` that FR-4 promises to display — the field is dead in MVP unless a plain-text (map-free) location input is silently smuggled into FR-3 without being named. This is a real spec inconsistency, not a nitpick: whoever implements FR-3 literally as written will produce a detail view with a permanently empty location slot, and whoever implements FR-4 literally as written will wonder where `Ort` is supposed to come from.

## High

3. **FR-10's heuristic has an undefined middle zone that swallows the most common meeting length.** "Kurze Termine (bis ca. 30-45 Min.)" are always unterbrechbar; "lange Termine (ab ca. 1,5-2 Stunden mit 3+ Teilnehmern)" are bitte-nicht-stören. Nothing defines the 45-minute-to-1.5-hour band — which is where the standard 1-hour meeting with 3+ people (arguably the single most common calendar event in any team) lives. The addendum's calibration table doesn't cover this case either (its examples are 30min/1, 2h/6, all-day/several, 15min/1, 0-participant focus block — none land in the gap). This isn't a "calibrate in architecture" detail; it's a hole in the decision table itself that needs at least a stated default (e.g., "when in doubt, default to unterbrechbar" or the reverse) before anyone can implement or test FR-10.

4. **No FR addresses team member onboarding or offboarding**, despite the tool being explicitly for a "festes 5-10-köpfiges Team" that will, in reality, not stay perfectly static over the prototype's life. There is no FR for adding a new member's OAuth connection, no FR for revoking a departing member's tokens and data, and no mention in Non-Goals that this is deliberately excluded. For a self-hosted, bus-factor-1 operated tool, "how do I remove someone's access and calendar data" is a first-class product question, not an operational footnote — especially combined with finding 8 below (token storage).

5. **No NFR or constraint addresses authentication/session security or network exposure of the tool itself.** The PRD specifies OAuth scopes for reading Outlook/Google, but says nothing about how team members log into the tool, how sessions are protected, or whether the self-hosted instance sits behind a VPN or is reachable from the public internet (it presumably needs to be, for OAuth callback flows). Given the tool aggregates every team member's real calendar content behind a display-only privacy rule (see finding 1), the login/session layer is exactly as security-critical as the OAuth scopes that got a whole subsection — but it gets zero mentions.

6. **No mention of OAuth token storage security.** FR-8 requires reading and storing full calendar data continuously, which requires long-lived OAuth refresh tokens for every team member sitting in the tool's database. A breach of that single self-hosted, bus-factor-1-operated database doesn't just leak "busy" statuses — it hands over live read access to every team member's actual Outlook/Google account. Nothing in §7 (Cross-Cutting NFRs) or §8 (Constraints) requires encryption at rest, secrets management, or even acknowledges this as a risk, despite the PRD otherwise being diligent about naming accepted risks explicitly (e.g., external-attendee PII, bus-factor-1 operations).

## Medium

7. **External-attendee PII risk is asserted as "accepted" without any retention or deletion policy, which is thin for GDPR-applicable data.** §4.4 Notes and §8 both acknowledge that names/emails of external customers/partners land in the backend "ohne separate Schutzmaßnahme," framed as an accepted risk based on team-internal trust. But the data subjects here (customers, partners) never consented to a new internal tool storing their contact data, and "team trust" is not a legal basis that covers third parties. Even for an internal prototype, this deserved at minimum a retention/deletion answer (e.g., "external attendee data expires when the source event does") rather than a one-line risk acceptance carried over unchanged from the brief. The PRD had the mandate to add this level of detail and didn't.

8. **No FR specifies how a native event's `Teilnehmer` field actually behaves for internal teammates.** FR-3 allows adding participants to a native event, and FR-10 uses participant count in the heuristic — but nothing says whether adding a teammate as a participant creates any linkage on their calendar, sends any signal, or is purely descriptive metadata used only for the heuristic. A team member creating an event with "Teilnehmer: Kollege X" would reasonably expect some effect on Kollege X's calendar; if there is none, that's a plausible source of confusion/complaints once used daily (exactly the UJ-1 "daily use" bar this PRD sets for itself in Success Metrics).

9. **Mehrpersonen-Ansicht selection persistence is scoped only within a session/view-switch, not across logins or devices.** FR-2's only persistence guarantee is "bleibt bestehen, wenn zwischen Tages- und Wochenansicht gewechselt wird." If the selection resets every time the tool is opened (a very plausible naive implementation), the core "in Sekunden sehen" JTBD (§2.1) is undercut by having to re-pick colleagues every session — worth a click-cost check against SM-1/SM-2 before assuming it's fine.

10. **No "as of" / staleness indicator is required anywhere, despite the whole product accepting several-minutes-stale data as normal.** The PRD is explicit and comfortable (§7, §8, Non-Goals) that sync lag of "wenige Minuten" is acceptable and by design. But nothing requires the UI to communicate *when* the shown status was last refreshed. A colleague acting on a "bitte-nicht-stören" reading that is, say, 8 minutes stale because of an unnoticed sync hiccup (see finding 11) has no way to know the data might be wrong — which is precisely the failure mode UJ-1's own edge case (status override) exists to patch, but only for self-reported inaccuracy, not for sync staleness.

11. **No FR/NFR addresses silent sync failure.** FR-5/FR-6 describe the happy path (new/changed event appears "spätestens nach dem nächsten Sync-Zyklus"), and §8 acknowledges that both providers' webhook mechanisms are unreliable (hence polling) — but nothing addresses what happens when polling itself fails: an expired refresh token, a revoked admin consent (explicitly called out as a live risk in Offene Fragen #2), or an API outage. For a bus-factor-1-operated tool with no monitoring/alerting FR mentioned anywhere, a silently-stopped sync for one team member would degrade to serving increasingly stale — and confidently displayed — availability data with no one aware until someone notices in person. Confidently-wrong-and-silent is a worse failure mode than the "no real-time" limitation the PRD spends multiple sections defending.

12. **Success Metrics have no defined measurement mechanism.** SM-1 ("tägliche aktive Nutzung"), SM-2 ("wahrgenommene Zeitersparnis"), and SM-3 ("Häufigkeit von Doppelbuchungen sinkt") are all stated qualitatively with no baseline, target threshold, or instrumentation plan. No FR anywhere mentions usage analytics/telemetry, so it's unclear how SM-1 (arguably the single Primary metric this whole prototype is judged by) would even be observed for a self-hosted 5-10 person tool beyond Dennis's personal impression. Given the PRD is otherwise rigorous about traceability (FR numbering, "validates FR-X" tags on every metric), leaving the metric itself unmeasurable is a notable gap.

13. **All-day events are semantically overloaded by FR-10.** "Ganztägige Termine gelten als bitte-nicht-stören" conflates "in office all day but heads-down" with "on vacation / entirely absent," which are different things a colleague needs to distinguish (one means "don't interrupt," the other means "don't bother, they're not here"). Showing both as the same "bitte-nicht-stören" status under the Privat-Default (no title visible to explain which) could actively mislead teammates about whether someone is reachable at all today — a real UX risk for exactly the JTBD (§2.1, "ob eine Kollegin ... gerade ansprechbar ist") this feature exists to serve.

## Low

14. **No stated cap on how many people can be selected in Mehrpersonen-Ansicht, in tension with the mobile NFR.** FR-2 lets a user select "eine Teilmenge der übrigen Teammitglieder" with no upper bound noted, while §7 claims "Alle Kernfunktionen (Ansichten, ...)" must work on mobile. Up to 9 columns in a day/week view on a phone screen is a real layout problem the PRD doesn't acknowledge, let alone resolve (e.g., via a mobile-specific cap or list fallback).

15. **Single-person, multi-account scenarios are unaddressed.** The Glossar defines a Teammitglied as having "eigenem Outlook- oder Google-Konto" (singular, either/or), but doesn't rule out — or plan for — a person who uses both a personal Google account and a work Outlook account, which is a common real-world pattern. Worth an explicit Non-Goal or Assumption if genuinely out of scope, since it currently reads as simply unconsidered.

16. **Time zone handling is unstated.** Nothing in the PRD confirms or excludes a single-time-zone team, and Mehrpersonen-Ansicht / heuristic time-of-day logic ("Tageszeit ist nachrangig") is silently assuming one. Should at least be added to the Assumptions-Index alongside the Google-Workspace and heuristic-threshold assumptions already listed there, for consistency with the document's own stated practice of surfacing assumptions explicitly.

17. **No FR addresses recurring-event interaction with Status-Override**, even though FR-14 (Serientermine) is explicitly deferred. Once recurring events ship, "override my status" raises an immediately obvious question (this instance only, or the whole series?) that the current FR-11 wording ("seinen eigenen ... Status") doesn't anticipate. Flagging now costs one sentence; discovering it during FR-14 implementation costs a rework.

18. **The "ask anyway" scenario for bitte-nicht-stören is neither supported nor explicitly excluded.** UJ-1's edge case covers *inaccurate* bitte-nicht-stören (self-override fixes it), but says nothing about a colleague who is accurately "bitte-nicht-stören" yet the interruption is urgent enough to justify anyway. FR-13's "notify when a waiting colleague becomes free" is explicitly rejected as unreliable — but the symmetric "let me flag urgency and interrupt anyway" isn't mentioned as accepted, rejected, or deferred. Worth a one-line Non-Goal for completeness, since it's a fairly predictable feature request once the tool is in daily use.

## Persona Notes (for traceability)

- **Skeptical developer/architect:** Findings 1–3, 6, 8, 11, 14, 17 — the PRD's "testable consequences" framing oversells how implementable several FRs are (FR-9's enforcement layer and FR-10's threshold gap are the two that would actually stall a competent implementer, not just require judgment calls).
- **End-user/team-lead:** Findings 4, 9, 10, 12, 13, 15, 16, 18 — most of the FR-level decisions hold up reasonably well for daily use, but staleness visibility, all-day semantics, and cross-session selection persistence are the three most likely to generate real user complaints within the first week of actual daily use.
- **Security/privacy-minded reviewer:** Findings 1, 5, 6, 7 — the OAuth-scope-and-provider-quota diligence in §8 is strong, but it's paired with a near-total silence on how the tool protects the data once it has it (storage, transport, auth), which is the more likely actual attack surface for a bus-factor-1 self-hosted deployment.

## What the PRD Got Right (not a complaint list only)

- Explicit `[ASSUMPTION]` tagging and a consolidated Assumptions-Index is good practice and should be the template going forward — several findings above (16) are really just "add one more line to a system you already have," not new process.
- FR-7 (Kein Zurückschreiben) and the associated Consequences are unambiguous and genuinely testable as written.
- The Non-Goals section is unusually disciplined about naming rejected features with a reason (e.g., FR-13's Out-of-Scope note on "colleague becomes free" notifications correctly ties the rejection to the sync-interval constraint rather than just asserting it).
- Counter-metric SM-C1 is a good sign of intellectual honesty — most PRDs at this stage don't bother instrumenting for their own failure mode (tool used for reading only, not for creating events).
