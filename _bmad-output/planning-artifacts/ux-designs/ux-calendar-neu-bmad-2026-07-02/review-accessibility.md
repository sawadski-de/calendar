# Accessibility Review — calendar-neu-bmad

## Overall verdict

The WCAG 2.1 AA target is taken seriously on paper: there's a dedicated Accessibility Floor section, a consistent "never color alone" commitment repeated verbatim across DESIGN.md's Do's/Don'ts and EXPERIENCE.md's Component Patterns, and the light-mode status colors really do pass AA where checked (computed 5.9:1–7.1:1 for interruptible/DND text-on-fill pairs, dark mode 8.2:1–9.4:1 for the same pairs — the docs' own uncertainty flag "implementation must verify actual rendered contrast" turns out to be unnecessarily modest, these pass comfortably). But the review surfaced one concrete, computed AA contrast **failure** in a Must-Have-NFR-critical color pair (sync failure text), and two real keyboard-operability gaps in the product's genuinely novel interaction patterns (prefilled double-click create, and floating-layer focus management) that the Accessibility Floor doesn't cover despite covering adjacent cases well. This is a credible, good-faith AA effort, not yet an AA-verified one — the items below are what stands between the two.

## Findings

- **critical** The sync-failure `errorText`/`errorIcon` token reuses raw `{colors.dnd}` (`#C2685F`) directly as caption-weight text color against `{colors.surface}` (`#1A1E24`) — computed contrast ≈ **4.33:1**, below the 4.5:1 AA threshold for normal text (the icon use of the same pair is fine at 3:1). This is the exact color pair backing the Sync-Transparenz Must-Have NFR's failure state (DESIGN.md `components.sync-indicator`; EXPERIENCE.md State Patterns "Sync failure (repeated/silent)"). Notably, the status-badge component correctly created a separate lightened `-text` variant (`{colors.dnd-text}` `#E7B7B0`, ≈8.2:1 against fill) for exactly this reason, but the sync-indicator component wasn't given the same treatment. *Fix:* use `{colors.dnd-text}` for `errorText`, keep raw `{colors.dnd}` only for `errorIcon`/borders where the 3:1 graphical-object threshold applies.

- **high** No keyboard equivalent is specified anywhere for double-click-to-create-prefilled. EXPERIENCE.md's Interaction Primitives and Accessibility Floor cover keyboard operability for the status-override flyout and both popover types explicitly, but the "Double-click to create, pre-filled" primitive and the "Appointment creation entry points" component row never state how a keyboard-only user reaches the pre-filled path — only the blank "+ Neuer Termin" button is a real, Tab-reachable control (EXPERIENCE.md Interaction Primitives, Component Patterns, Accessibility Floor). *Fix:* state explicitly that individual time slots are focusable via `Tab` and that `Enter`/`Space` on a focused slot opens the same pre-filled create form as a double-click.

- **high** No focus-management spec (trap while open, restore-on-close) for the status-override flyout or either popover type. The Accessibility Floor lists `Tab`-reachability, `Enter`/`Space`-open, arrow-key navigation, and `Esc`-close, but never says where focus goes after closing, nor whether `Tab` is trapped inside an open flyout/popover — a common real-world failure mode for exactly this kind of custom floating-layer component (EXPERIENCE.md Accessibility Floor; Interaction Primitives "Escape/outside-click closes floating layers"). *Fix:* add that closing any flyout/popover returns focus to its trigger element, and that `Tab` cycles only within the open layer.

- **medium** Interactive hairline borders fall well short of the 3:1 non-text-UI-component threshold: `{colors.border}` (`#2B3038`) against `{colors.bg}` (`#12151A`) computes to ≈**1.38:1**. This is the `buttonBorder` for the status-override control and the `ghostBorder` for the create/add-person pills — controls whose tappable boundary is defined only by this outline, with no fill differentiating the resting state (DESIGN.md `components.status-override-control`, `components.appointment-create-entry`). The light-mode equivalent (`border-light` on `bg-light`/white) is similarly low. *Fix:* either explicitly accept this as covered by the 1.4.11 exemption (icon+text inside already signals "control") and say so, or raise the resting-state border contrast for these specific interactive pills to ≥3:1.

- **medium** `{colors.accent-light}` (`#2E9B99`) is documented as reused for "links, focus rings" in light mode (DESIGN.md Colors) — contrast against white ≈**3.35:1**, which clears the 3:1 UI-component/focus-ring bar but fails the 4.5:1 normal-text bar if used as literal link *text*, as the prose states. *Fix:* restrict accent-light to non-text graphical uses in light mode (rings, icons, active-state fills), or specify a darker dedicated link-text value.

- **medium** No `prefers-reduced-motion` consideration anywhere in DESIGN.md or EXPERIENCE.md, despite hover states, flyout/popover open transitions, and glow-shadow effects being named parts of the visual language ("no hover-lift... no drama on interaction" describes intent but not a reduced-motion floor). *Fix:* add one line to the Accessibility Floor: transitions shorten/disable under `prefers-reduced-motion`.

- **medium** The status-override flyout is specified as a fixed 216px width in the reference direction (`.status-flyout { width: 216px; }`), holding translated strings — German "Bitte nicht stören" is already 19 characters, and other languages could run longer — plus a right-aligned "AKTIV" tag competing for the same fixed space. DESIGN.md's token table doesn't carry an explicit width, but it's derived from this literal artifact. *Fix:* specify `min-width` + intrinsic sizing rather than a fixed px value for any component holding translated option labels.

- **medium** No live-region behavior is specified for the sync-failure state transition. The Accessibility Floor addresses static screen-reader labeling of status blocks but not how a screen-reader user learns that the sync-timestamp indicator flipped from neutral to failed asynchronously (no page reload). *Fix:* specify the sync-indicator's failed-state container as `aria-live="polite"` (or `role="status"`).

- **low** The status-block glyph is the same shape (a filled "●") for both interruptible and DND in the reference direction file (`.status-block .glyph`), differentiated only by CSS color class — DESIGN.md's "small glyph + text label" language somewhat overstates the icon's independent role, since the text label is doing all the non-color differentiation work today. Not a live violation (the label is always present per spec), but it removes the safety margin if a label is ever hidden/truncated. *Fix:* give the two states visually distinct glyph shapes, not just distinct colors, as defense-in-depth.

- **low** Following directly from the above: nothing in EXPERIENCE.md's Responsive & Platform section (which already flags small-screen multi-person layout as `[OPEN QUESTION]`) connects that open question to the color-alone requirement — a status label truncated on a narrow column would silently degrade the signal to color-only. *Fix:* add a floor rule that status text labels must never truncate/ellipsize, even under horizontal scroll or narrow layouts.

- **low** Left-anchored, LTR-specific structural choices (status-badge `borderSide: left only, 3px`; the fixed-left time-gutter; icon-then-label ordering) aren't expressed as logical/direction-aware properties, and RTL isn't discussed in either document. Current requirements are German/English only (both LTR), so this isn't an active violation, but it's worth noting now while the component contracts are still being fixed. *Fix:* note in DESIGN.md that `border-left`/left-anchoring is LTR-specific and will need `border-inline-start`/logical-property treatment before any RTL language is added.

- **low** The time-gutter is a fixed 64px column sized for a 24h "08:00"-style label; neither document addresses whether a 12-hour AM/PM locale format (a longer string) would fit, which is a plausible variant even within German/English. *Fix:* confirm the gutter width tolerates the longest anticipated time-label format, or pin the app to 24h format regardless of locale.
